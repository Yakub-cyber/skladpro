# skladpro (веб-кабинет) — инструкция для сессии

Ты работаешь **только с этим репозиторием**. Бэкенд и мобильное приложение живут
в отдельных репозиториях и в отдельных сессиях. Не предполагай ничего об их коде.
Если задача упирается в API — опиши, какой контракт нужен, и остановись; менять
бэкенд отсюда нельзя.

## Что это

Веб-кабинет B2B SaaS ERP для оптовой торговли (аналог CloudShop / МойСклад).
React 18 + Vite + zustand (persist в localStorage) + Tailwind, роутинг
react-router. Ходит в собственный бэкенд по `VITE_API_URL` (эндпоинты `/v1/...`),
работает офлайн через outbox.

## Главное правило — учёт

Остаток, себестоимость и долг **не правятся точечно**. Любое изменение — только
документом через движок. Функция, которая делает `stock: p.stock + n` напрямую,
— это баг, даже если она удобная.

Так уже убраны `receiveStock` и `adjustStock`. Не воскрешай их и не пиши
аналоги: пока такая функция лежит в публичном API стора, ею кто-нибудь
воспользуется, и учёт снова разъедется.

Правила, которые нельзя нарушать:

- **Отрицательный остаток разрешён** для продажи и отгрузки. В опте это норма:
  товар приехал, продали с колёс, приходную накладную проведут вечером. Минус —
  сигнал оператору («проведи приход»), а не ошибка. Так работают CloudShop,
  МойСклад, 1С. Запрещать минус можно только для перемещения и списания.
- **Отрицательный баланс клиента разрешён** — это предоплата. Никаких
  `Math.max(0, ...)` на балансе и остатке: обрезка нулём тихо теряет деньги, а
  при откате создаёт долг из воздуха.
- **Количество хранится в базовых единицах.** «20 упак» при factor 12 — это 240.
  Умножение делает `normalizeItems()` из `lib/units.js`, и **только оно**.
  Функция идемпотентна: если у позиции уже есть `unitFactor`, повторно не
  умножает. Не добавляй новых точек умножения — их уже было три, и это чуть не
  дало ×144.
- **Любая операция должна корректно откатываться.** Провели → отменили → цифры
  вернулись к исходным. Не «не ушли в минус», а именно вернулись.

## Открытые задачи, по приоритету

1. **С1 — источник истины.** Сейчас клиент ведёт полноценную вторую бухгалтерию
   (`applyDocToState`, `applyOrderStock`, `lib/batches.js`, `lib/cost.js`), а
   сервер ведёт свою из реестра движений. Две реализации одной логики неизбежно
   разойдутся.

   Решение принято: **источник истины — сервер.** Значит клиентский расчёт
   партий, FIFO и себестоимости **удаляется**, а не переводится в
   «оптимистичный режим» — иначе это та же вторая бухгалтерия с оговоркой.

   Оптимистичный апдейт оставить минимальный, только чтобы UI не мигал:
   `stock -= qty`, без партий и без себестоимости. Пришёл ответ сервера —
   перетёрли. Себестоимость в момент продажи показывать не нужно: неверная
   цифра хуже, чем «считается».

   Остатки хранить не полем в карточке товара, а отдельной таблицей по складам
   (как `stock_balances` на сервере). Это заодно закрывает К5.

2. **К5 — перемещение между складами клонирует товар.** `warehouseSlice.js`
   создаёт новую карточку с новым `id` и артикулом `CC-05·МАГ` вместо переноса
   остатка. Один товар превращается в два: аналитика разваливается, при
   перемещении обратно суффикс наращивается, а парсер начинает выбирать между
   двумя почти одинаковыми названиями случайно. Делать после С1.

3. **С2 — парсер сопоставляет по цифре объёма.** `matchProduct` в `lib/ai.js`
   считает долю совпавших токенов, и токен `0.5` даёт совпадение 1 из 1, то есть
   100 % уверенности на случайности. Результат зависит от порядка строк в
   каталоге. Правило: если все совпавшие токены — числа или объёмы, это не
   совпадение.

4. **M1 — у парсера нет состояния «не уверен».** `confidence` считается, но в
   интерфейсе не показан; бейдж бинарный «каталог / новая». Нужны три состояния:
   точно (>85), проверь (60–85, с показом 2–3 кандидатов на выбор), не нашёл.

5. **С3 — парсер переделать на retrieval-first.** Сейчас LLM получает голый
   текст и **сочиняет названия**, а выбор SKU делает локальная регулярка. Надо
   наоборот: искать кандидатов по своему каталогу, отдавать модели короткий
   список и просить **выбрать id**. Это единственное, что возьмёт разговорные
   заказы вроде «дай 20 колы, 10 фанты» — сейчас они не разбираются вообще.
   **Не начинать, пока не набраны 50–100 настоящих заказов** от оптовиков:
   иначе пороги будут подогнаны под выдуманные примеры.

6. **С4 — лимиты тарифа только на клиенте.** Подписка лежит в
   `settings.subscription` в localStorage, лимиты считаются в сторе. Devtools →
   enterprise за десять секунд. Проверка должна быть на сервере.

7. **С5 — роли не защищают маршруты.** `App.jsx` не закрывает ни один маршрут
   по роли, `nav.js` только фильтрует меню. Курьер открывает `/money` прямой
   ссылкой.

8. **Мелочи:** дробное количество + маркировка списывает `Math.ceil(qty)` кодов;
   клиента с предоплатой можно удалить (проверка ловит только должников); цена
   из текста заказа игнорируется; в UI написано «DeepSeek», а работает OpenAI
   через ProxyAPI; `hasBatches` = `Array.isArray`, поэтому услуга с `batches: []`
   уходит в партионную ветку.

9. **Уборка:** удалить папку `supabase/` (1226 строк SQL от прошлой архитектуры,
   вводит в заблуждение); вынести `BUDGET_6M.md`, `BUDGET_MIN_2M.md`,
   `PRICING.md`, `UNIT_ECONOMICS.md` в приватный репозиторий — юнит-экономика не
   должна уезжать вместе с кодом.

## Как проверять

Тестов много, и это не значит, что они что-то ловят: на момент аудита 336
зелёных тестов не находили ни одного из пяти критических багов. Они проверяли
функции по отдельности, а ломался стык.

Поэтому каждый тест на учёт — **цикл**, и он обязан падать на старом коде:

```
предоплата: баланс 0 → addMoneyTx(5000) → -5000 → cancelMoneyTx → 0   (не 5000)
отгрузка:   остаток 10 → продали 100 → -90 → отменили → 10            (не 100)
упаковки:   приход "20 уп" при factor 12 → 240                        (не 20)
```

Проверяй **точные значения** (`toBe(-5000)`), а не мягкие (`toBeLessThanOrEqual(0)`)
— мягкие пропускают ровно тот баг, который чинишь.

Если тест пришлось обновить под новое поведение — покажи старую и новую строку
рядом и объясни, почему новое верно. Обновление теста под код — самый частый
способ спрятать регрессию.

Перед коммитом: `npx vitest run` и `npx vite build`.

## Чего не делать

- Не создавать функций, пишущих `stock` или `balance` напрямую.
- Не возвращать обрезку нулём.
- Не добавлять новых точек умножения на `unitFactor`.
- Не коммитить несвязанные изменения вместе с правкой учёта — если в рабочем
  дереве оказались чужие файлы, разбери их отдельным коммитом или откати.
- Ключ ProxyAPI не должен требоваться от пользователя. Сейчас экран просит
  завести свой ключ на proxyapi.ru — оптовик этого не сделает. Ключ должен быть
  серверный. Не углубляй эту схему.
- Не коммитить `.env` и ключи. Помни, что любая переменная с префиксом `VITE_`
  попадает в публичный бандл.
